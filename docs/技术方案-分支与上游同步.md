## 1. 目标

在保留 **自建 NAS + NPM `/subw/` 子路径**、**自建 subconverter `/subapi`** 集成的条件下，按需吸收 CareyWang 上游 UI 与构建链更新（Vite 等）。

**`hjsmaster` 是唯一面向交付的功能主分支**；`origin/master` 仅作上游镜像参考，不直接用于 NAS 部署。

## 2. 分支职责

| 分支 | 职责 |
|------|------|
| **`hjsmaster`** | **我们的主分支**：NPM 子路径、版本 API `/version.txt`、HouJia 品牌与文档 |
| **`master`** | 追踪 **CareyWang/sub-web** 的 `master`，本地开发时可 fetch 对比 |
| `feature/*` | 短期功能分支，合并后删除；长期能力应进入 `hjsmaster` |

约定：

- GitHub **默认分支** = `hjsmaster`。
- 不在 `origin/master`（CareyWang）上直接做 NAS 定制提交。

## 3. 远程与跟踪关系

```bash
git remote -v
# origin   https://github.com/CareyWang/sub-web.git   # 上游只读参考
# fork     git@github.com:HouJia/sub-web.git          # 我们的 GitHub，推送 hjsmaster
```

| Remote | 用途 |
|--------|------|
| `fork` | 推送 `hjsmaster` 及发布用 tag |
| `origin` | CareyWang 上游，fetch 后 diff 合入 `hjsmaster` |

## 4. 与 subconverter 的协作

| 项 | sub-web | subconverter |
|----|---------|--------------|
| 公网路径 | `/subw/` | `/subapi/` |
| 后端 API | `VITE_SUBCONVERTER_DEFAULT_BACKEND` → `https://<域名>:<端口>/subapi` | 容器 `:25500` |
| 页眉版本 | 请求 **`/subapi/version.txt`**（纯文本） | 提供 `GET /version.txt` |
| 分支 | **`hjsmaster`** | **`hjsmaster`** |

详见 subconverter 仓库：`docs/技术迭代-NAS部署与NPM暴露.md`。

## 5. 同步 CareyWang 上游

```bash
git fetch origin master
git checkout hjsmaster
git merge --no-ff origin/master   # 或 cherry-pick 特定 commit
# 解决冲突后：优先保留 hjsmaster 的 .env.example、vite base、backendService.js
yarn build && yarn lint   # 若有
git push fork hjsmaster
```

**合并时注意保留的 HouJia 差异**：

- `VITE_BASE_PATH=/subw/`（`.env.example`）
- `src/services/backendService.js` → `/version.txt`
- `src/config/constants.js` 后端地址逻辑
- `nginx.subw.conf`、`Dockerfile`
- 页眉标题与 `VITE_PROJECT` 指向 `HouJia/sub-web`

## 6. NAS / NPM 部署

```bash
cp .env.example .env
# 必改：VITE_BASE_PATH、VITE_SUBCONVERTER_DEFAULT_BACKEND
./deploy/nas/deploy-to-qnap.sh
```

容器默认：`subweb`，端口 `58081`，NPM 反代 `/subw/` → 容器 80。

## 7. 迭代流程

1. 从 `hjsmaster` 拉功能分支（可选）或直接在小改动上 commit。
2. 本地 `yarn dev` / `yarn build` 验证。
3. push 到 `fork/hjsmaster`。
4. NAS：`./deploy/nas/deploy-to-qnap.sh`。
5. 若 subconverter 也有 API 变更，先升级后端再重建前端。

**维护**：变更分支模型或 NPM 约定时，同步更新本文与 `README.md`。
